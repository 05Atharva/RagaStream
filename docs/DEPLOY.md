# Deploying RagaStream: backend on Render, Android APK with EAS

You'll put the API on Render's free plan, point Supabase at it, and build an APK that talks to it. Allow about 45 minutes the first time. After that, an update is a `git push` for the backend and one command for the app.

```
Phone (APK) ──HTTPS──► Render: ragastream-api (FastAPI + yt-dlp + Node)
     │                        │
     └──── sign-in ──► Supabase (Auth + Postgres) ◄────┘
```

## 0. Before you start

- The code is on GitHub (`main`), and Render will deploy from there.
- You need a **Render** account (sign in with GitHub) and an **Expo** account (expo.dev, free).
- On your laptop you need Node 20+ (you have 24), plus the `.env` values from `backend/.env` for step 1.
- Supabase is already set up (`docs/AUTH_SETUP.md`).

## 1. Deploy the backend on Render

1. Go to **Render dashboard → New → Blueprint**, connect GitHub, and pick the `RagaStream` repo. Render reads `render.yaml` and proposes one web service, **ragastream-api** (Docker, region Singapore, free plan).
2. Render asks for the values marked secret. Copy them from `backend/.env`:

   | Key | Where it comes from |
   |---|---|
   | `SUPABASE_URL` | `https://jprsscsopqnwiihkgued.supabase.co` |
   | `SUPABASE_KEY` | Supabase → Project Settings → API → **anon / publishable** key |
   | `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Project Settings → API → **service_role** secret. Keep it only on Render, never in the app. |

   `AUDIO_LINK_SECRET` is generated by Render, and `OWNER_EMAILS` and `YTDLP_COOKIES_FILE` are preset.
3. Click **Apply**. The first build takes about 5 minutes (it installs Python packages, yt-dlp and Node).
4. Note the service URL, for example `https://ragastream-api.onrender.com`. Open `<URL>/health`. It should show `{"status":"ok","service":"ragastream-api"}`.

If your URL differs from `https://ragastream-api.onrender.com` (Render adds a suffix when a name is taken), use yours everywhere below, including `frontend/eas.json`.

### 1b. YouTube cookies (needed on cloud servers)

YouTube often blocks data-centre IPs with "Sign in to confirm you're not a bot". Your laptop worked because it's a home connection. Render needs cookies from a signed-in YouTube session:

1. In a desktop browser, sign in to YouTube. A **spare Google account** is safest, because the cookies give access to that account.
2. Export cookies for `youtube.com` in Netscape format, for example with the browser extension "Get cookies.txt LOCALLY", which exports locally only. Save the file as `cookies.txt`.
3. Go to Render → **ragastream-api → Environment → Secret Files → Add**. Filename: `cookies.txt`. Paste the contents and save. Render mounts it at `/etc/secrets/cookies.txt`, which is what `YTDLP_COOKIES_FILE` points to.
4. **Manual Deploy → Deploy latest commit.**

Without the file, the server still starts, but logs a warning and playback may fail. Cookies expire after a few weeks, so re-export them when songs stop playing (see Troubleshooting).

### 1c. The free plan sleeps

Render's free plan stops the server after about 15 minutes with no requests. The next request waits about 1 minute while it wakes. The app is built for this:
- A signed-in user opens straight into their library.
- Requests wait up to 75 s.
- The access check retries.

To avoid the wait, choose one:
- an uptime monitor (for example UptimeRobot, free) that pings `<URL>/health` every 10 minutes, which keeps it awake within the free 750 h/month; or
- the Starter plan.

Server memory (caches, import jobs) resets when it sleeps. That's expected.

## 2. Point Supabase at the deployed backend

Go to Supabase → **Authentication → URL Configuration → Redirect URLs** and add:

```
https://ragastream-api.onrender.com/auth/return**
```

This is the page Google sign-in lands on before returning to the app. Keep `ragastream://**` (the installed app) and `exp://**`. The Site URL stays `ragastream://`. Leave `http://*.nip.io:8000/auth/return**` too, if you still develop on your Wi-Fi.

## 3. Build the APK with EAS

Run these from `frontend/`:

```powershell
npm install -g eas-cli          # once
eas login                       # your Expo account
eas init                        # once: links the project, adds extra.eas.projectId to app.json
```

Commit the `app.json` change that `eas init` makes. Then check that `frontend/eas.json` → `build.preview.env.EXPO_PUBLIC_API_URL` is your Render URL from step 1.

```powershell
eas build --platform android --profile preview
```

- EAS builds in the cloud (10–20 minutes on the free queue). It runs `npm ci`, applies `patches/` automatically through `postinstall`, and signs the APK with a key it manages for you. Answer **Yes** when it offers to generate an Android keystore.
- When it finishes, it prints a link and a QR code. Open it on the phone, download the `.apk`, and install it. Android asks you to allow installs from your browser or Files app once.
- The `production` profile also builds an APK, and raises `versionCode` automatically for each build. Use `--profile production` for builds you'll share.

**Why not Expo Go anymore?** The APK is a real app: its own icon, background playback with lock-screen controls, and no development server. `frontend/.env` is not used by the build; `eas.json` carries the public settings (API URL, Supabase URL, anon key). The anon key is public by design: the database gives it no table access.

## 4. Check the installed app

1. Open it. You should see the splash, then sign-in, or your library if you were already signed in.
2. Sign in with email, then sign out and **Continue with Google**. It should come straight back to the app.
3. Play a song, lock the phone, and wait a few minutes. Music continues, and the lock screen shows the title with play and pause.
4. Skip, seek, Smart Shuffle, and Autoplay at the end of a playlist.
5. Library → Import: paste a Spotify or YouTube playlist link and let it finish.
6. Sign out: the music stops.
7. With a second account, sign up. You should get the approval email; approve it in Settings → Requests.
8. Leave the app unused for 20 minutes, then open it. It opens into your library and catches up once the server is awake, without logging you out.

## 5. Updating

| What changed | Do this |
|---|---|
| Backend code | `git push` to `main`. Render redeploys automatically (`autoDeploy`). |
| yt-dlp needs an update (songs 403 or fail) | Render → **Manual Deploy → Clear build cache & deploy**. This installs the newest yt-dlp. |
| App code | Raise `"version"` in `app.json` (e.g. 1.0.1), then `eas build -p android --profile production` and install the new APK over the old one. Data and sign-in are kept. |
| YouTube cookies expired | Re-export `cookies.txt`, replace the Secret File, and redeploy. |

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| "Can't reach RagaStream" on first open | The server is asleep and took more than ~2 min, or the URL is wrong | Open `<URL>/health` in a browser. Check `EXPO_PUBLIC_API_URL` in `eas.json` and rebuild. |
| Songs won't play; Render logs say "Sign in to confirm you're not a bot" | YouTube is blocking Render's IP | Add or refresh `cookies.txt` (step 1b). |
| Songs fail with 403 from googlevideo | yt-dlp is out of date | Clear build cache & deploy. |
| Google sign-in returns to the login screen | The Render landing URL isn't allow-listed | Step 2. The Supabase table `auth.flow_state.referrer` shows where it went. |
| No approval email | Gmail app password, or the `OWNER_EMAIL` secret | Supabase → Edge Functions → notify-signup → Logs (see `docs/AUTH_SETUP.md`). |
| Signed out by itself | The session really expired (a refresh failed) | Sign in again. Server outages now return 503, which keeps you signed in. |
| Lock-screen controls missing | You're in Expo Go | They only exist in the APK. |

Secrets never go in git: `backend/.env`, `backend/cookies.txt` and keystores are ignored. Render, Supabase and EAS keep their own copies.
